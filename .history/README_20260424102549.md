## Overview

This pipeline bridges two worlds that initially appear disconnected: the **CAPTUS/HybPiper bait-relative coordinate space** (where per-locus MSAs and phylogenetic reconstruction live) and the **reference genome coordinate space** (where gene annotations, variant calls, and functional predictions live). The key insight is that these two systems do not need to be merged at the read level — only via a one-time lookup table built by mapping bait sequences to the genome.

```
Bait FASTAs ──► CAPTUS extraction ──► Per-locus MSAs ──► IQ-TREE2 gene trees ──► HyPhy MEME
                                                │                    │
                              (bridge: minimap2/BLAT + bedtools)     └──► ASTRAL species tree
                                                │                                │
Reference genome + GFF ──► Gene models ──────► Unified locus table       phyloFit neutral model
                                                │                                │
                                         SIFT · VEP · SnpEff ◄────────── GERP scores
```

## Conceptual framework — two coordinate systems

### The bait-relative coordinates

CAPTUS takes each species' raw reads, assembles contigs, and maps them against the bait sequences as the reference. The output is a per-locus FASTA/alignment where every column position is defined **relative to the bait**, not relative to any chromosome. This is all you need for phylogenetic reconstruction, HyPhy, and GERP. The 160-species MSA for a given locus has no knowledge of what chromosome it sits on — nor does it need any.

### The chromosome coordinates

The reference genome with its GFF provides gene models, exon boundaries, reading frames, and protein products. This annotation layer lives entirely in chromosome coordinates.

### The bridge — a one-time lookup, not a remapping of reads

Map the bait FASTAs (not reads) to the genome once. The result is a BED file and, after intersection with the GFF, a **unified locus table** like:

| locus_id   | chr:start–end        | gene_id     | feature_type  | notes                 |
| ---------- | --------------------- | ----------- | ------------- | --------------------- |
| locus_0042 | Chr3:1200000–1400000 | BRCA2_ortho | CDS exon 4–7 | codon-aware alignment |
| locus_0117 | Chr7:4500000–4600000 | unknown     | intergenic    | GERP only, skip SIFT  |
| locus_0503 | Chr1:890000–910000   | MYB_TF      | exon + intron | use CDS columns only  |

This table is built once and used as metadata throughout — it tells you which loci are protein-coding (eligible for SIFT), which are intergenic (GERP only), and how to translate MSA column positions to chromosome positions for annotation.

## Stage 1 — Bait-to-genome mapping

### Why splice-awareness matters

We are going to use BLAT or minimap2 to find the position of the baits sequences on the B. masoniana genome. Why not using BLAST? Let's see.
Hyb-Seq baits are typically designed from CDS or transcriptome sequences. A bait sequence is therefore a **continuous stretch of exonic sequence**, but in the genomic reference, introns interrupt those exons. When BLAST maps such a bait, it either splits the alignment into two separate HSPs (one per exon flank) or penalises the hit as a large gap/mismatch. BLAT and `minimap2 -ax splice` model this as a spliced alignment and output a single coherent interval.

> **If the baits were designed from genomic DNA** (not from CDS or a target file such as Angiosperms353), intronic splits are not a concern and plain `blastn` works cleanly. But as we work from transcriptome data, the sequences might be affected by splicing, therefore we must use BLAT or minimap2.

> **minimap2 is not long-read only.** The long-read presets are `map-ont` and `map-pb`. The `splice` preset works on any cDNA/exon-derived sequence regardless of length.

For this reason, we choose minimap to do the alignment of the baits on the B.masoniana genome. But with what option?

**On the `-ax splice` question**

The baits range from 200 bp to ~6,000 bp, with the bulk between 500–1,500 bp. These are not short Illumina reads, they are assembled contigs used as probes. The `-ax splice` preset in minimap2 is designed for cDNA/mRNA sequences mapped to a genome, which is actually a good match here *if* the baits were designed from transcriptomic sequences, because it tolerates the large intron gaps between exons. So the preset is conceptually appropriate.

However, `-ax splice` carries some assumptions tuned for RNA-seq reads (typically 100–300 bp). For sequences in your 500–6,000 bp range, the more correct preset is actually **`-ax splice:hq`** (high-quality spliced, better for longer cDNA) or simply **`asm5`** / **`asm10`** if your baits are from a closely related genome assembly rather than transcripts.

This description clarifies everything. Your baits are **transcriptome-derived CDS sequences** (from *Begonia luzhaiensis* transcriptome, filtered against the cucumber genome annotation, plus Angiosperms353 matches). This confirms that `-ax splice` is the correct preset — the baits are continuous exonic sequences that will span introns when mapped to the *Begonia masoniana* genome.

There is one additional nuance though. Your baits come from a **divergent transcriptome** ( *B. luzhaiensis* , an Asian species) being mapped to what is presumably a different *Begonia* species genome (*Bmas.fa* — likely  *B. masoniana* ?). The genetic distance between the bait source and your reference matters for minimap2 preset tuning.

The `-ax splice` preset uses relatively strict parameters optimised for mapping a transcript back to its own genome. For cross-species mapping at the within-genus level (which is your situation), you want to relax the mismatch tolerance. The recommended adjustment is:

The key additions are `-C5` which reduces the penalty for non-canonical splice sites (important because splice sites may differ slightly between *B. luzhaiensis* and  *B. masoniana* ), and `-u b` which tells minimap2 to search for GT-AG splice motifs on both strands rather than inferring strand from the sequence alone — sensible when mapping across species where strand signal may be weaker.

However, looking at your BED output, your mapping quality scores are all 60 (maximum mapq), which suggests the within-genus divergence is not causing any real alignment difficulty. Your `-ax splice` script as written is already working well. The duplicate-line issue described in my previous message (same contig appearing with both `+` and `-` strand) is the only genuine problem to fix, and that is purely a `bamtobed` issue, not a minimap2 preset issue.

So to directly answer your original question:  **`-ax splice` is correct for your data** . The baits are CDS-derived, the mapping is cross-species within the same genus, and your mapq=60 results confirm it is working. The only change needed to your script is the `samtools view -F 2308` filter and the `-split` flag on `bamtobed` before intersecting with the GFF.

The ASTRAL species tree captures incomplete lineage sorting across 160 species, making it a more accurate neutral model for GERP than an NJ or concatenation tree. Use `species_tree_astral.nwk` as the `--tree` input to `phyloFit` in Stage 3a.

## Stage 4 — Purifying selection with HyPhy MEME

MEME allows ω to vary **across branches at the same site**, unlike FEL which estimates a single ω per site averaged over the whole tree. This means a site can be under purifying selection in most lineages but show episodic acceleration in one or a few branches — a biologically realistic model for most empirical datasets.

We generate outputs using `script_hyphy.sh` or `script_hyphy_array.sh`.

This script homogenize the headers of the MSA files and remove symbols that cannot be processed by HyPhy (squarre brackets for exemple). We use as well the command `hyphy rmv` to remove the potential stop codons in the sequences. Finaly, the command hyphy meme is used to produce the output in `pathout="output_meme/${locus}.json"`

### Interpreting MEME output

Each site in the JSON reports two ω rate classes with a mixing proportion:

| Field          | Meaning                                             |
| -------------- | --------------------------------------------------- |
| `omega1`     | ω for the constrained branch class (typically < 1) |
| `omega2`     | ω for the episodically selected class              |
| `proportion` | fraction of branches assigned to `omega1`         |
| `p-value`    | significance of episodic departure from neutrality  |

For **purifying selection** inference, focus on sites where `omega1 < 1` with a high `proportion` value — meaning the majority of branch length at that site is constrained. Sites with a significant p-value and `omega2 > 1` indicate episodic positive selection in a subset of lineages.

Parse JSON outputs with the `hyphy-analyses` Python utilities or with the `hyphy-vision` web interface.

GERP++ begins with a pre-defined neutral tree that supplies both the total neutral rate across the entire tree and the relative length of each individual branch. The key point is where those branch lengths come from.

`gerpcol` requires a tree file in standard Newick format  *including branch lengths* . If the branch lengths are in units other than substitutions per site, it may be necessary to scale the input tree using the `-s` or `-n` parameters. 

So there are **two valid approaches** to provide the neutral rate:

**Option A — use phyloFit (the "proper" way):** Run phyloFit on putatively neutral sites (classically 4-fold degenerate synonymous sites) to estimate a substitution model, then use the resulting `.mod` file's tree (with ML-estimated branch lengths in substitutions/site) as input to `gerpcol`. This is what the notes recommend, and what large genome studies do.
**What are 4-fold degenerate synonymous sites?** They are synonymous codon positions where any nucleotide change is silent. For example, substitute a C with an A, G, or T will not change the final amino acid produced by this sequence. They are effectively single-nucleotide neutral sites where selection pressure doesn't apply, so no purifying selection.
We don't have any neutral site as introns in the dataset, we just and just exons. Therefore, we must use 4-fold sites to establish the neutral rate on Hyb-Seq data set.

**Option B — supply a tree with pre-existing branch lengths directly:** If you already have a phylogenetic tree with branch lengths in substitutions per site (e.g., from IQ-TREE or RAxML run on your alignment data), you can pass it directly to `gerpcol -t`. The branch length reflects the neutral substitution rate along the branch — i.e., the expected number of neutral substitutions per site.
These trees do not reflect the neutral substitution. The branches length is based on relative substitution rate between nucleotides and infer the branch length in expected substitution per site.

#### The critical issue for *your* dataset

This is where your study design creates a real consideration. Your loci are **all coding sequences** (exons from annotated genes). Using these same loci to estimate the neutral rate via phyloFit is **circular and incorrect** — coding sites are under purifying selection, so they will *underestimate* the neutral rate, and your GERP scores will be biased.

The standard solution is to use **4-fold degenerate (4D) sites** for neutral rate estimation — synonymous third codon positions where any nucleotide change is silent. As we don't have any neutral site and just exons in the dataset, we must use these sites that may vary without selection pressure. They are effectively neutral sites. Since your `.fna` alignments are in-frame codon alignments, you *can* extract 4D sites from them. This is precisely why phyloFit is recommended for coding sequence datasets.

GERP scores evolutionary rate shifts column-by-column on the multi-species alignment. It requires a **neutral substitution rate model**, estimated from 4-fold degenerate sites.

A positive RS (rejected substitutions) score indicates conservation above the neutral rate. Columns with high RS scores overlapping HyPhy-detected sites under purifying selection are high-priority candidates.

## Good news: you have what gerpcol needs

Your rescaled species tree from IQ-TREE already has branch lengths in substitutions per site, estimated from your actual alignment data. Gerpcol requires the tree in Newick format including branch lengths, where branch lengths should be in units of substitutions per site. Your `species_tree_rescaled.treefile` satisfies this requirement directly — you can pass it with `-t` to `gerpcol`.

## The key question: is it a good *neutral* rate?

This is the important nuance. Your IQ-TREE rescaling used `-s concatenated_MSA.fna` with `-m MFP+MERGE`, meaning the branch lengths were estimated from your  **coding sequence alignment** . As I mentioned before, coding sites are under purifying selection, which tends to **compress branch lengths** relative to true neutral evolution. So technically, these branch lengths represent the *observed* substitution rate across your loci, not the neutral rate.

However, there is important context for your specific case:

**Arguments that this is acceptable for Begonia:**

* Your loci are single-copy nuclear genes spread across many functional categories — not exclusively highly conserved sequences. The average constraint across hundreds of genes is much less severe than, say, using only conserved housekeeping genes.
* Begonia is a genus with substantial divergence across species. With enough phylogenetic depth, branch length estimation is fairly robust.
* For **within-genus comparative genomics** (rather than deep vertebrate-style GERP), the relative ranking of GERP scores between sites matters more than absolute calibration. The bias is systematic and affects all sites equally.
* The phyloFit/4D-site approach assumes you *can* identify reliably neutral sites — with a target capture dataset of a few hundred genes, 4D site extraction is possible but the resulting alignment may be sparse, making phyloFit estimation noisy. Your IQ-TREE estimate from the full alignment may actually be *more stable* despite the slight conservative bias.

**When you would strictly need phyloFit:**

* If you are comparing GERP scores to published thresholds from other studies (e.g., RS > 2 to define "constrained")
* If you need absolute constraint scores for functional annotation
* If reviewers or your methods require it explicitly

## Practical recommendation

Your current tree is a reasonable and defensible neutral rate proxy, especially for a within-Begonia study. To make it bulletproof methodologically, you could add one step:

```bash
# Extract 4D sites from your codon-aligned .fna files
# PHAST's msa_view can do this if you have a GFF/annotation
msa_view concatenated_MSA.fna \
    --4d \
    --features annotation.gff \
    -o FASTA > 4d_sites.fa

# Fit neutral model on 4D sites only
phyloFit --tree species_tree_rescaled.treefile \
         --subst-mod REV \
         --out-root neutral_model \
         4d_sites.fa
# → neutral_model.mod

# Extract tree for gerpcol
grep "^TREE" neutral_model.mod | sed 's/TREE: //' > neutral_tree.nwk
```

But if you lack a per-locus GFF annotation (likely, given your target capture design), extracting 4D sites is non-trivial. In that case,  **your rescaled IQ-TREE species tree is a practical and justifiable choice** , and you should simply document in your methods that branch lengths were estimated from the coding sequence alignment under `MFP+MERGE` with topology fixed to the ASTRAL species tree, acknowledging that this may slightly underestimate the neutral rate.

## Stage 6 — Variant calling and annotation

If per-species BAMs are available from read mapping:

```bash
# GATK per-species GVCF (run per species)
gatk HaplotypeCaller \
     -R reference.fasta \
     -I species_X.bam \
     -O species_X.g.vcf.gz \
     -ERC GVCF

# Joint genotyping per locus
gatk CombineGVCFs -R reference.fasta \
     $(for s in gvcfs/*.g.vcf.gz; do echo "--variant $s"; done) \
     -O combined.g.vcf.gz

gatk GenotypeGVCFs -R reference.fasta \
     -V combined.g.vcf.gz -O genotyped.vcf.gz

# Annotate with SnpEff
snpEff ann -v reference_db genotyped.vcf.gz > annotated.vcf
```

SnpEff labels each variant with functional class: `synonymous_variant`, `missense_variant`, `stop_gained`, `splice_region_variant`, etc. Filter to the bait intervals using the bridge BED file.

## Stage 7 — Deleterious allele prediction with SIFT

SIFT requires **protein-coding loci only** — use the bridge table to filter. SIFT4G is the recommended modern implementation.

SIFT scores each amino acid substitution based on sequence conservation at that position across the multi-species alignment:

- Score **≥ 0.05** → tolerated
- Score **< 0.05** → predicted deleterious

```bash
# Build SIFT4G database from reference proteins
SIFT4G_Create_Genomic_DB \
    -genome reference.fasta \
    -dbName sift4g_db \
    -gff reference.gff

# Run SIFT4G on the annotated VCF
SIFT4G_Annotator \
    -c annotated.vcf \
    -d sift4g_db \
    -r sift_results/
```

> SIFT scores are most meaningful at alignment positions covered by **≥ 10 diverse sequences**. Check per-locus alignment depth before interpreting results.

## Stage 8 — Integration and prioritisation

Combine all annotation layers into a single candidate table. A variant is a high-confidence functional candidate if it meets all three criteria:

- High GERP RS score (strongly conserved site)
- `omega1 < 1` with high branch proportion in HyPhy MEME (pervasive purifying selection)
- SIFT score < 0.05 (predicted deleterious substitution)

```python
import pandas as pd

gerp    = pd.read_csv("gerp_scores.tsv", sep="\t")
hyphy   = pd.read_csv("hyphy_meme_summary.tsv", sep="\t")  # parsed from MEME JSON
sift    = pd.read_csv("sift_results.tsv", sep="\t")
bridge  = pd.read_csv("bait_locus_annotation.tsv", sep="\t")

merged = (bridge
    .merge(gerp,  on=["locus_id", "msa_column"])
    .merge(hyphy, on=["locus_id", "msa_column"])
    .merge(sift,  on=["locus_id", "variant_aa"], how="left"))

candidates = merged[
    (merged["gerp_rs"]         > 2.0)   &
    (merged["meme_omega1"]     < 1.0)   &
    (merged["meme_proportion"] > 0.9)   &   # most branches constrained
    (merged["sift_score"]      < 0.05)
]

candidates.to_csv("high_priority_candidates.tsv", sep="\t", index=False)
```
